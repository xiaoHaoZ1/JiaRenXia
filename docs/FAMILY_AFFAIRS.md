## 1. 定位更新

一句话：**家里管事的人用的家庭管家。** 以家人关系为底座，把家里的人和事（生日、缴费、人情、保障、安全）记在一处。

使用的人：

1. **家里管事的人**：上有老、下有小的中间一代，替父母操心保险、医保、养老金、人情往来。主要用户。
2. **其他家庭成员**：通过微信收到“家人共享”文件（第 9 节），导入后以自己为中心看称谓；新婚夫妻可以在婚礼上“碰一碰”合并两家（第 10 节）。
3. **父母**：在自己手机上用守护。

与 VISION 的关系：仍然“关系优先”。家事模块的每条记录都挂在人物上——谁的保单、谁家的人情、给谁办的事。本地优先、家庭资料不上传、App 内不注册、App 不联网的原则不变（见 AGENTS.md）；家事模块可以在设置里关闭，不用的人看不到，保持简单。

## 4. 应用锁（V0.5 第 1 批，已于 2026-10-09 下线）

**已下线。** 代码连同 `data/security/`、锁屏页、我的页安全卡片与 `androidx.biometric` 依赖一并删除，需要恢复时从 Git 历史取回。下线理由：忘记密码时没开指纹的用户只能清空全部数据，对一个没有服务器也没有客服的本地 App 来说，这是真实的数据丢失面；而它防的「别人拿到你没锁的手机打开 App」，手机自带的锁屏密码已经覆盖大半。家庭资料的安全主张仍是不联网、不上传、不注册，与应用锁无关。

以下为下线前的设计，仅作留档。

- 入口：我的 → 安全 → 应用锁，默认关闭。
- 4–6 位数字密码（输入两次）；可选指纹 / 面容解锁（新增依赖 `androidx.biometric:biometric:1.1.0`）。
- 何时上锁：冷启动；切到后台超过设定时间后回来（立即 / 1 分钟 / 5 分钟，默认 1 分钟）。从通知点进来也要先解锁。
- 只保存密码的 PBKDF2-HMAC-SHA256 哈希（随机盐，迭代次数使一次校验约 100 毫秒），不存明文。连续输错 5 次冷却 30 秒，之后每次翻倍，最长 10 分钟。
- 开启后，Android 13 及以上隐藏“最近任务”里的界面预览（`setRecentsScreenshotEnabled(false)`）；不使用 `FLAG_SECURE`，不影响截图。
- 忘记密码：开了指纹的，用指纹解锁后重设；没开的，只能“清空全部数据”（输入“清空”二字确认），之后可从备份恢复。开启应用锁时明确提示先备份。
- **守护不受影响**：应用锁只拦主界面。守护的确认响铃界面、紧急拨号、状态通知一律不经过应用锁。
- 第一次进入人情或保障时，如果没开应用锁，提示一次“建议开启应用锁”。

**数据库加密：暂不做**（2026-10-09 应用锁下线后依然成立）。

- Android 10 及以后出厂的手机必须使用文件级加密，App 私有数据在开机后首次解锁前无法读取。
- 云备份规则已排除全部数据（`data_extraction_rules.xml`）；换机迁移会带上家庭数据，这是有意的。
- SQLCipher 会让安装包增大数 MB，还要迁移现有数据库，主要只防 root 后直接读文件。
- 日常风险是别人拿到你没锁的手机打开 App，这交给手机自带的锁屏密码，App 内不再做二次锁。以后确有需要再单独评估。

## 5. 家庭事项提醒（V0.5 第 2 批）

### 5.1 模板

| 模板 | 默认重复 | 默认提前 | 说明 |
|---|---|---|---|
| 保险缴费 | 每年 | 15、3 天、当天 | 第 7 节保单的缴费提醒也用它 |
| 居民医保缴费 | 每年 | 7 天、当天 | 各地缴费期不同，日期由用户按当地通知填写 |
| 养老金资格认证 | 每年 | 30、7 天 | 按当地社保要求填写 |
| 证件到期 | 不重复 | 60、30、7 天 | 身份证、驾驶证、护照等，名称可改 |
| 体检 | 每年 | 7、1 天 | |
| 自定义 | 不重复 | 1 天、当天 | 可改为每月 / 每年 |

提前提醒可多选：当天、1、3、7、15、30、60 天。App 不内置任何地区的固定日期。

### 5.2 内容

- 关联家人（可选；不选表示全家的事）
- 标题（按模板自动生成，如“妈妈的居民医保缴费”，可改）
- 日期、重复（不重复 / 每月 / 每年）、提前提醒
- 金额（可选）、备注、提醒开关

### 5.3 办完与重复

- 点“已办”：不重复的事项移到“已办”；重复事项自动排到下一期，并记下本次办理日期。
- 下一期从首次日期按周期数推算，避免月底漂移：1 月 31 日“每月” → 2 月 28/29 日 → 3 月 31 日。2 月 29 日的“每年”事项，平年按 2 月 28 日。
- 过了日期还没点“已办”：列表标红“已逾期 N 天”，不重复发通知。

### 5.4 通知

- 三类提醒（生日与纪念日 / 家庭事项 / 联系）各有自己的每日“提醒时间”，在「我的 → 提醒」中分别设置（默认 09:00）；任一类提醒开着，每日检查就运行。某类数据在其时刻过后被改成“今天到期”时，当天立即补跑一次（只发该类当天尚未通知过的提醒，不重复打扰）。
- 我的 → 提醒 新增“家庭事项提醒”总开关，与“生日与纪念日提醒”各管各的。
- 新通知渠道“家庭事项”，可在系统设置里单独关闭。
- 文案：“今天要办：妈妈的居民医保缴费”；“3 天后（10月15日）：爸爸的养老金资格认证”。点通知打开该事项。

### 5.5 数据

- 新表 `family_tasks`：id、person_id（可空；删除该人物时一并删除）、kind（模板）、title、首次日期、repeat、已办到第几期、上次办理日期、amount（分，可空）、note、enabled、policy_id（可空，第 7 节用）、created_at、updated_at。
- 新表 `family_task_offsets`：task_id、days_before（与 `reminder_offsets` 同样规范化存储）。
- 数据库 v3 → v4；备份 schemaVersion 4，旧备份没有这一项时恢复为空。

### 8.1 会员码绑定设备（2026-10-04 确定；2026-10-06 废弃）

> 2026-10-06：**本节废弃，不实施。** 用户选定联网会员方案（设计见 `docs/membership/`）：在官网购买兑换，每台设备在 App 里输入邀请码联网开通，开通后永久离线可用。本节保留作决策记录；其中“JRX1 作废、不做兼容”的决定继续有效。

目标：激活码不能随手转发、倒卖。在离线校验的前提下，“付款立刻到账”和“码不能转手”不能兼得：码必须在付款、知道是哪台手机之后再签发，因此接受签发要等待。

- **设备码**：
  - 由 `Settings.Secure.ANDROID_ID`（Android 8+ 按“应用签名 + 用户 + 设备”区分）加固定盐做 SHA-256 得出。显示为 10 位、含 1 位校验位（`XXXXX-XXXXX`），字母表去掉 0/O、1/I/L 等容易看错的字符，方便抄写和在电话里念。原始 ANDROID_ID 不显示、不导出。
  - 只在用户打开会员卡片或激活对话框时读取，启动时不读。
  - 同一签名下卸载重装不变；恢复出厂、换手机后会变。调试版和正式版签名不同，设备码也不同，实测要用正式版。
- **绑定码（JRX2）**：
  - 每台手机一个码。原文 = version 2 + 订单序号（账本按爱发电订单号分配的递增序号）+ 签发日 + flags + 设备哈希（与设备码同源）；签名沿用现有 P-256 密钥对。
  - App 校验签名，并要求码里的设备哈希等于本机的；不一致时提示“这个激活码属于另一台手机”，不笼统地说“无效”。
  - 码只对那台手机有效，私信被截图、转发都不要紧，发码渠道不限。
- **购买与签发**：
  1. 我的 → 会员 → 去购买：用浏览器打开爱发电下单链接，附 `custom_order_id=设备码`，并在 `remark` 预填“设备码：XXXXX-XXXXX（请勿修改）”，方便在后台直接看到。
  2. 买家付款后，爱发电的固定自动回复告诉买家“激活码会在 X 小时内私信发送”。
  3. 签发：运行 `LicenseGen bind`，输入爱发电订单号和设备码 → 校验设备码格式与校验位 → 查账本（同一订单累计不超过 5 台）→ 签出 JRX2 码 → 写入账本。
  4. 把码私信发给买家，买家在 App 里“输入激活码”粘贴。
- **一单最多 5 台**：
  - 第 2–5 台：买家私信“订单号 + 设备码”，用同一条命令签发。
  - 换手机或恢复出厂后设备码会变，需要重签。离线无法作废旧手机上的码，所以换绑也计入累计台数；累计满 5 台后由人工判断是否放行（真换机放行，频繁换绑拒绝）。
  - 账本是 CSV（订单号、订单序号、设备码、签发时间、备注），和私钥放在同一备份目录；含买家订单信息，不入库。
- **备份与恢复**：绑定码照常随备份。恢复到同一台手机，会员自动恢复；恢复到别的手机校验不过、不写入，提示“会员绑定在原来的手机上，换机请联系 2107290326@qq.com”，并显示本机设备码。家人共享、碰一碰仍不含激活码。
- **JRX1 作废，不做兼容**：还没有正式发布过任何版本，App 只认 JRX2。开发期生成的 1–500 号 JRX1 码和 CSV 一并作废；旧备份里的 JRX1 码恢复时直接忽略；开发测试机升级后用 JRX2 码重新激活。
- **以后自动化（可选，App 不用改）**：
  - LicenseGen 加 `sync` 命令，由 Windows 计划任务定时运行：`/api/open/query-order` 拉新订单、读 `custom_order_id` → bind → `/api/open/send-msg` 私信发码（爱发电限频 10 次/秒、1000 次/小时）。爱发电 API token 和私钥一样不入库。
  - 第 2–5 台与换机请求来自私信（开放 API 不能读私信），以后可以交给 Agent 处理，但要有护栏：签不签由 bind 按规则判断（订单已付款、累计不超过 5 台），Agent 绕不过去；Agent 读不到私钥；买家私信一律当作不可信输入；超出规则的转人工。
- **已知局限**：
  - 挡不住改包破解，任何离线校验都一样。正式版目前没开 R8（`isMinifyEnabled = false`），开混淆要另做一轮回归。
  - 读取 ANDROID_ID 属于收集设备标识。上架国内应用商店，一般要在隐私政策里说明，且不能在用户同意前读取（项目还没有隐私政策）。
  - 付款后要等签发，电脑关机时等得更久。
- **实现前待验证**：

## 10. 碰一碰结为夫妻（V0.7）

> 已删除（2026-10-21）：碰一碰与婚礼祝词已从家人侠移除，本节仅作历史设计存档。

场景：新郎新娘在婚礼现场，把两部手机背靠背碰一下，资料自动交换、直接结为夫妻；两边的家庭关系合并，各自都能看到对方的家人和正确的称谓（岳父、公公、小姨子等）。对方家人带着新称谓飘进各自的半颗心，两部手机并排举给来宾看，拼成一颗完整、同步跳动的心。

- **条件**：两边都已经创建了“我”，一男一女；家人里还没有配偶，或者已录入的配偶就是对方（同名同性别）。否则提示“你的家人里已经有配偶了”。
- **三种模式**：首次合并（结为夫妻、合并两家，双方握手确认一致后各写入一次）、已配对纪念（已结为夫妻的两部手机再碰，只播仪式、不交换也不写入家庭资料）、彩排（任一方选择，双方都不写入、不建立正式配对）。配对后另有“更新家人资料”：补充式更新，先出预览（新增几人、几条关系、冲突几条）再各自确认，冲突字段永远保留本机值、不静默覆盖。
- **流程**：
  1. 准备：两边打开 共享与连接 → 碰一碰结为夫妻。首次进入先各自选择连接方式——一台“主动感应（读卡）”、一台“等待感应（卡片）”，两台必须相反；成功一次后本机记住上次成功的角色，仍可手动更换。可打开“彩排模式”。已配对手机还可选“纪念仪式”或“更新家人资料”。
  2. 碰一碰：两人面对面把手机背靠背一碰（像碰杯）。首次合并约 1–2 秒交换并写入（彩排不写入）；连上时震两下、完成时长震一下。中途分开了再贴一下，凭会话 id 从中断处继续（会话 2 分钟超时作废）。前置检查在贴上时就做，不通过直接提示原因、不交换资料。
  3. 合心：交换完约 1.5 秒，两部手机同时开始过渡动画——对方家人带着从“我”的视角算出的新称谓依次飘进本机的半颗心，心渐渐填满，最后一起跳动。纪念模式改为显示双方姓名与祝福。
  4. 展示：全屏、最亮。新郎手机显示左半颗心、新娘右半颗心（称谓与左右仍按性别，与连接方式无关）；两部手机并排拼成一颗完整的心。心跳按碰一碰时对好的共享时钟同步；心按实际尺寸（毫米）画。点屏幕出现“换边”、“查看我们的家”（彩排时为“再来一次”）、“完成”；纪念仪式可“重播”（只重演动画，不重新导入）。
  5. 连接方式：初次两台各选一个相反方式，等待页有大按钮“交换连接方式”；贴上没反应时两台都要切换（一台切换无法通知另一台，界面如实说明）。有的手机当卡片端会把钱包默认卡交给对方（如 OPPO ColorOS 15 安全芯片为内置 eSE、钱包有默认门禁卡时，读卡端只能读到门禁卡、没有 IsoDep），读卡端会提示交换方式。
- **配对与确认**：
  - 首次成功合并后，两部手机建立持久配对（配对标识 + 对方家人→本机家人的完整映射）。此后任何一次再碰都按配对走：默认纪念，可选更新资料。
  - 旧用户“本地已录入配偶”不等于“手机已配对”：首次碰时同名同性别的已录入配偶只是候选，确认页明确列出“将与已录入的 X 对应”，确认后才建立配对；取消则不做合并。
  - 配对记录不对称（一边有一边没有、或两边配对标识不同）时不静默退化为全量合并：进入恢复确认，由用户选择重新配对或取消。
  - 碰一碰的“改用家人共享”入口先选择对方发来的共享文件，再进入密码与确认流程；取消文件选择保留碰一碰页面，不进入缺少文件的导入页。
  - 配对数据只存在本机（数据库表 spouse_pairing / tap_person_map / tap_device），不进备份、不进共享文件；备份恢复或换机后配对自动失效——设备无法冒充已配对对象；“清空所有数据”一并清除（设备级角色偏好随清空数据重置）。
- **合并规则**：
  - 两边的家人和关系都加进来，再加上两人之间的夫妻关系。
  - 每部手机的“我”不变：新郎手机上的“我”还是新郎，称谓各自从自己的角度计算。
  - 可信同一人只有两类：配对时持久化的“对方人物→本机人物”映射，以及随资料包携带的来源标记 oid——人物是“从本机出发的导出物”时 oid 记本机人物 id，回流时本机核对姓名性别后认回（合并后再更新不会把自家亲戚当成新人问）。除此之外一律不自动合并。
  - 对方来源人物 id 与本机已有人物 id 相同且姓名性别一致时复用该 id（幂等重放不产生新人）；id 相同但信息不符按无关冲突处理，对方生成新 id。
  - 姓名、性别、关系位置三者一致只产生“可能是同一人”候选，由本机用户在确认页勾选后才合并（对方录入的“我”或配偶是阻塞候选，不确认整次不能完成）；不按称谓推断血缘，不自动删除历史重复人物。
  - 映射人物只补缺失的生日与手机号，类型相同但值不同的重要日期记入冲突清单并在更新预览中显示，冲突字段永不静默覆盖。
  - 写入原子性：家人合并与配对/映射在同一数据库事务提交，任何一步失败整体回滚，不留半截。卡片端只在收到读卡端 DONE（= 对方已写入成功）后才提交本机，读卡端提交失败发 REJECT，一端已写另一端未写时下次碰面按“配对不一致”恢复。
  - 同一请求重放、断开重贴、页面重建，都凭配对映射、oid 与资料指纹安全恢复，不会产生重复写入。
  - 头像不经碰一碰传输（数据量太大），之后可以通过第 9 节的分享补齐。
  - 家庭事项、人情往来、保障一览不交换，属于各自的私密数据。
- **纪念日文案**：准确阳历结婚日期已知时，按自然日期显示相伴天数（结婚当天为第 1 天）与完整周年数，纪念日当天缝口加金色星光；农历日期、缺年份、日期在未来或两边日期冲突时不编造数字，显示普通祝福并提示核对日期。除结婚日期外，双方还交换恋爱/领证纪念日：每种类型两边记录一致且含年份时，按“相恋 → 领证 → 结婚”顺序列出各自时长（“相恋 8 年 3 个月 · 领证 6 年 · 结婚 5 年”）；任一种类型一边缺失或不一致只影响该类型并提示回家核对，其余一致类型照常显示。
- **婚礼祝词**：首次合并的合心动画里，两部手机各显示一个词拼成祝词（默认“喜结|连理”，左机“喜结”、右机“连理”）。我的 → 婚礼祝词 可换成预设（永结同心 / 百年好合 / 佳偶天成 / 白头偕老）或自定义（每词至多 4 字，超长自动缩字号），并可全屏预览动画。祝词是本机设置，随 HELLO 带给对方；两端设置不一致时以读卡端为准，保证两机拼读的是同一对词。
- **技术方案**：
  - 用 NFC 传数据，不联网：一台用读卡模式、另一台模拟卡片（HCE），角色由用户选择并与性别无关，双向交换压缩后的家庭资料。55 人的家庭大约几 KB，1–2 秒传完。
  - 协议 HELLO v4：版本 4 | 会话 id | 姓名 | 性别 | 家人数 | 标志位（bit0 彩排、bit1 更新意向）| 时钟 8B | 本人人物 id | 已有配对 id | 会话 nonce 16B | 配偶姓名 | 纪念日条数 + 每条（类型 + 日期）：结婚/领证/恋爱各至多一条（v3 为单条结婚纪念日）| 婚礼祝词 UTF8（尾部可选，缺省按“喜结|连理”，两端不一致以读卡端为准）。配对 id = SHA-256(两台 nonce 排序拼接) 前 16 字节 hex，双方独立推导一致；状态码新增 REJECT(4) 并携带原因码（性别不符/不是录入的配偶/配对不符）；纪念模式只走 HELLO 协商与 DONE，不生成不传输资料包。
  - DONE 带共享的合心开始时刻；两部手机须同为 v4（旧版提示升级）。震动用 VIBRATE（普通权限）。
  - 只需要 NFC 权限（普通权限，不弹授权框），不需要 INTERNET 权限。
  - 安全：NFC 只在几厘米内有效；两部手机都打开碰一碰页面并贴上才交换（打开页面并贴上即视为同意结为夫妻、交换并写入资料）；一男一女与配偶相容检查不通过则不交换；彩排不写入；纪念与更新不匹配不写入；交换的内容和备份一样先经过完整校验。
- **前提与备选**：
  - 两部手机都要有 NFC 并打开。没有 NFC 的，改用第 9 节的微信分享，导入时选“和我结为夫妻”，合并规则相同（等待页有“没有 NFC”备用入口直达共享导入）。
  - 真机测试需要两部带 NFC 的手机。
- **验证**：合并规则（含多层去重、id 冲突、重放幂等）做成纯逻辑单元测试；NFC 收发用模拟通道测试分包与重组、拒绝原因码与会话续传；配对协商（首次/纪念/彩排/更新/不对称恢复）用双 ViewModel 模拟两台手机测试；两部真机实测。

**实现说明（V0.7 落地；V1.0 重写为配对式三模式）**：

- `domain/merge/TapPairing`：纯 JVM 配对模型与协商——`SpousePairing`（配对 id、对方本人 id、本机配偶 id、对方显示名、完整来源人物→本机人物映射、上次会话与资料指纹、上次成功角色）；`TapNegotiator` 依双方 HELLO 决定 首次合并 / 纪念 / 更新 / 彩排 / 配对恢复 / 对方换机 六种走向（更新需双方都开了“更新家人资料”，单方意愿按纪念走并提示）；`TapMemorial` 纯函数产出纪念文案（相伴天数、周年、各纪念日时长行、冲突提示）。
- `data/tap/RoomSpousePairingStore`：配对持久化在 Room v9——`spouse_pairing`（单行配对记录）、`tap_person_map`（来源人物 id→本机人物 id）、`tap_device`（本机角色偏好等硬件偏好，不随备份/人物清理删除，仅“清空所有数据”清除）。`SpousePairingStore` 接口不变；配对与设备偏好均不进备份、不进共享文件，恢复备份即失配对，需重新碰面建立。
- `domain/merge/SpouseMerge`：纯 JVM 合并计划——前置校验（一男一女、配偶相容）；自动匹配只认持久映射、oid 来源标记与精确 id；结构遍历（父母/子女/兄弟姐妹/配偶多层 BFS）只产出“同一人候选”，进入确认页由用户勾选批准后才并入映射（阻塞候选不确认则不能完成）；id 冲突重新生成、重复关系/电话/日期跳过、映射人物只补缺失字段、同类型不同值重要日期记入冲突清单、输出全量映射供配对持久化。`MergePlan` 由 `BackupManager.importMerge` 单事务写入——家人资料与配对/映射经事务内回调同一事务提交，失败整体回滚；重放同一计划为幂等空写。
- `nfc/TapProtocol`：纯 JVM APDU 状态机。AID `F04A52580001`（category other），CLA 0x80，INS：PUT_HELLO 0x10 / STATUS 0x20（200ms 轮询；0 等待 1 就绪 2 就绪-双确认 3 取消 4 拒绝+原因码 5 待确认）/ PUT_DATA 0x30 / GET_DATA 0x40（4B 偏移语义 → 断开重贴续传）/ DONE 0x50；读卡端先 GET_DATA 读对方资料、再 PUT_DATA 写自己的，卡片端收齐即双向完成；DONE 携带 8 字节共享开始时刻，且是卡片端提交写入的唯一触发（读卡端的 CONFIRM 早于候选决策不可信，DONE 证明对方已写库）；资料包 = 4B 总长 + 32B SHA-256 + Deflate(backup.json zip)，其中每个人物可带 oid（本机收到它时的来源 id，回流防重复）；接收端 `parsePlan` 全量校验；会话 2 分钟超时；取消/拒绝后本会话作废，其余命令一律 6A82。
- `nfc/TapHostService`（HCE）+ `nfc/TapSession`（单例活动标记，页面外一律 6A82）。服务必须在 manifest 里声明 `<service android:permission="BIND_NFC_SERVICE">` + `HOST_APDU_SERVICE` intent-filter + `host_apdu_service` meta-data 指向 `res/xml/apduservice.xml`——0.8.1 漏了声明，`dumpsys nfc` 里查不到本应用，两机贴合毫无反应（0.9.0 修复，`TapManifestTest` 常驻校验）。读卡端 `enableReaderMode(NFC_A | NFC_B | SKIP_NDEF)`，IsoDep 超时 3s，在等待/交换/展示/错误页都保持读卡模式（展示时关掉会让系统把仍贴着的对方当普通标签，弹“无支持该卡片的应用”）。卡片端不设首选服务（setPreferredService）：小米等机型感应到读卡器会把钱包/交通卡页面弹到前台，应用一离开前台系统就撤销首选服务并解绑正在通信的 HCE 服务，连接当场断开；本应用 AID 唯一，不设首选也会路由到 TapHostService。卡片在整个页面期间保持应答（不随 pause 停用），被钱包页面盖住时交换照常进行。页面生命周期内只有一张 `TapCard`，pause/resume 重建不丢会话，断开重贴可续传；读卡端错误映射：链路断开（IOException/TagLost）→ 回等待页提示再贴，协议错误 → 错误页可“重试”；读到非 IsoDep 标签（门禁卡/公交卡/对方钱包卡片抢占）给出可操作的换方式提示。卡片端 HCE 链路断开（onDeactivated）且交换未完成时回等待页提示再贴，会话保留。
- `ui/tap/`：`TapScreen`/`TapContent`/`TapViewModel` + `HeartShow`（合心过渡与展示：物理尺寸、共享时钟心跳、新家人带称谓飘入、换边、纪念星光与重播）；称谓由 `domain/merge/TapReveal` 在合并后的内存关系图上推导（彩排同样适用）。`TapViewModel` 持会话 nonce、协商模式与配对状态机，写卡提交与资料指纹核对，REJECT 原因码透传双方 UI。资料包 = `BackupManager.exportTapPayload`（共享文件同构 ZIP，purpose="tap"，无头像无私密模块；纪念模式完全不调用导出）。
- 备选路径：共享导入页选定“我”且满足前置时出现“和我结为夫妻（合并两家）”，与碰一碰同一合并写入。
- 调试：我的 → 调试 → 预览拼心展示（左 / 右）（仅 debug 构建）。

### 10.1 碰一碰互加亲人（V1.2）

> 已删除（2026-10-21）：碰一碰与婚礼祝词已从家人侠移除，本节仅作历史设计存档。

场景：我和任何一位亲人（不限性别、不限关系，如表哥）碰一碰，把各自圈好的家人资料互换，再从对方带来的人里挑要加进自己家的。

- **流程**：分别从「共享与连接 → 碰一碰结为夫妻」「共享与连接 → 碰一碰互加亲人」进入对应流程（两台手机必须进同一个入口，否则互不交换并提示）→ 互加亲人接着先圈“分享给对方的家人”（复用第 9 节的选人界面，“我”必选、默认全选、有分支预设、断开有提醒）→ 贴上即双向互发各自圈选的资料包 → 传完就可以分开，之后各自在本机独立完成。
- **“他是谁”**：收到对方资料后先认对方本人——指认成我家已录入的某个人（同性别、且不是“我”），或“我家里还没有他”：声明他是本机某人的某种关系（父亲/儿子/哥哥……按对方性别过滤选项），新建这个人并挂上声明的关系；声明与本机记录矛盾（如又给我添一位父亲）时退回重选并说明原因。指认/声明后对方带来的人才能和本机人物比对出“可能是同一人”。
- **挑人与预览**：对方带来的人逐条列出（“对方本人”“对方的X”，本人恒选），勾选要加的；勾了但经对方关系连不到本人（中间人没勾）先提醒可返回补选。然后是第 16.7 节的合并预览（新增/疑似同一人/冲突/关系矛盾），本机确认才写库——没有“双方都确认”的等待。
- **持久映射**：确认时对方→本机人物映射存入 person_alias（与共享导入同一机制）；下次再碰同一个人，凭映射自动认出对方本人，直接进挑人页。已加过的人幂等，不再重复建。
- **与结为夫妻的边界**：互加亲人不做性别校验、不查配偶、不放合心动画、不建立夫妻配对记录、不需要双方同时确认；性别校验与配对/纪念/更新语义只属于结为夫妻。
- **协议**：HELLO 升到 v4，新增 1 字节用途字段（0=结为夫妻，1=互加亲人），协商在配对判定之前先比对用途。v3 及更早版本不识别互加亲人——版本不同提示两部手机都更新（不会让旧版把亲属资料当夫妻包合并）。协商出“互加亲人”后两侧资料就绪即交换；传输完成后读卡端发 DONE 收尾，此后断开不再影响本机决策（识人/选人/预览/完成页不随 NFC 状态或对方离开回退）。

## 16. 接收家人资料与合并（V1.1，2026-10-05 确定）

目标：一个人整理好的家庭资料，其他家人能直接拿来用、接着补充；各自补充的成果能累积到一起。推广时谁也不想在手机上从头打字。

原先的问题：新装必须先创建“我”才能恢复备份或接收资料；共享导入只能整体替换；“从备份恢复”会把共享文件当备份整库恢复，接收方的“我”变成分享者（0.9.4 及之前的缺陷，已修复：恢复流程按文件用途分流，`BackupManager.restore` 只接受备份文件）。

实现顺序：16.1–16.3 欢迎页、恢复确认与接收流程（第 1 批，已有数据时仍为整体替换）→ 合并引擎与写入（16.5、16.6，第 2 批）→ 合并接收界面与对应关系持久化（16.3 默认合并、16.4、16.7，第 3 批）→ 16.9（第 4 批）。

### 16.1 欢迎页

- 没有“我”时，启动动画之后进入欢迎页，不再直接进入“创建我”；“清空所有数据”后也回到欢迎页。
- 两个入口：
  - **新建我的家庭**：创建“我” → 添加家人（原引导流程）。在“创建我”页按返回回到欢迎页。
  - **用已有资料开始**（说明：家人发来的共享文件，或自己的备份）：系统文件选择器（先定位「下载」）→ 输入密码 → 按文件用途自动分流：共享文件 → 接收流程（16.3）；备份 → 恢复确认（16.2）；其他 → 提示“无法识别这个文件，请确认是家人侠的备份或共享文件”。
- 页面写明微信的打开方法：在微信里点开文件 → 右上角“…” → “用其他应用打开” → 家人侠。新装用户这样打开会直接进入接收流程（原有能力）。
- 取消选择、密码错误、导入失败都停在欢迎页：不会先建一个临时的“我”，也不留半套数据（恢复与导入本身是单事务）。
- 欢迎页与“我的 → 从备份恢复”共用同一套恢复流程，分流规则、提示文案一致。

### 16.2 恢复确认与“我不是 X”

- 恢复确认对话框写明“恢复后，‘我’是 X”；本机已有数据时再提示“将覆盖当前全部数据，且无法撤销”。
- 备份里的“我”不是本人时（例如把备份文件当成共享文件发给了亲戚），可点“我不是 X”：这份备份改按家人共享处理，进入接收流程选“我是谁”。改按共享处理时只保留与共享文件相同的内容（人物、手机号、关系、重要日期、提醒偏好、头像），去掉事项、人情、保单、联系记录、自定义称呼与设置——这些是对方的私密数据。
- 备份里没有“我”时不显示该按钮；恢复后照旧进入创建“我”。

### 16.3 接收流程（共享文件统一入口）

- 第一步永远是“你是谁？”：从列表选（每行“姓名（分享者的 X）”），或选最后一项“资料里没有我”。
- 选中某人后显示“从你的角度看”预览：最多 8 位家人及其称谓（核心家人在前，分组与排序同家庭页），以及“另有 N 位暂时算不出称谓”。预览只读，用来确认没选错人。
- **资料里没有我**：填写自己的姓名，选“我是 [资料里某人] 的 [父亲 / 母亲 / 儿子 / 女儿 / 丈夫 / 妻子 / 哥哥 / 姐姐 / 弟弟 / 妹妹 / 兄弟（长幼未知）/ 姐妹（长幼未知）]”，性别由所选关系决定。只建这一条关系，不按称呼推断血缘。关系须满足 16.6 的约束：对方已有两位父母时不能选父亲/母亲，对方已有配偶时不能选丈夫/妻子。选兄弟姐妹且对方记有父母时，照旧询问“是同父同母的亲兄弟姐妹吗？”。新的“我”与导入在同一事务写入，同样先显示“从你的角度看”预览。
- 本机没有任何人物：直接导入（原 importShare 行为）。
- 本机已有数据：默认**合并**（16.4–16.7），预览确认后写入；“整体替换”降为次要操作，仍需二次确认并建议先备份。
- 满足夫妻前置条件时，“和我结为夫妻（合并两家）”照旧保留，规则见第 10 节。合并计划以本机的“我”计算（0.9.4 及之前误用了文件里所选人物的 id，导致此入口实际从不出现）；点“和我结为夫妻”并确认预览，即确认对方就是自己的配偶（已录入的同名配偶直接认作对方）；对方录入的与自己同名同性别的配偶视为自己；名字不同时，在“你是谁”里选中那条记录即确认“那就是我”。

### 16.4 同源更新与首次对齐

- **同源更新**：双方资料出自同一份分享。比如你分享给妈妈，她导入后补充自己那一支再分享回来，或者反过来。导入与合并都保留人物原 id，同一个人在两边 id 相同，可以直接认回，用户只需看预览确认。这也是“分工录入”的方式：一个人先录主干，各家补各自那一支再发回来。
- **首次对齐**：两人各自从零录入，人物 id 不同。以“你是谁”为起点（文件里的“你” ↔ 本机的“我”），沿父母 / 子女 / 兄弟姐妹 / 配偶逐层找出“可能是同一人”的候选，由用户确认；确认结果持久保存（16.5 第 1 条），以后再接收就和同源更新一样。
- 文件里有与本机“我”同 id、同性别的人时，“你是谁”默认选中此人，用户可以改选。
- 已有数据又选了“资料里没有我”：先请用户指认一位“两边都有的家人”（资料里的某人 = 本机某人，须同性别）作为起点；两边确实没有共同的人时，改用“我是 [资料里某人] 的 [关系]”建一条连接关系。若文件与本机已有同 id 或已保存的对应关系，可以直接以它们为起点，不必再指认。

### 16.5 合并规则（同源更新与首次对齐共用）

在第 10 节 SpouseMerge 规则的基础上推广：去掉“一男一女”、配偶相容检查和自动添加的夫妻关系。碰一碰继续使用夫妻专用的前置检查与配对记录。

1. **认人**（用户的明确指认优先于下面的自动规则）：
   1. 起点：用户在“你是谁”或 16.4 中指认的人。
   2. 已保存的对应关系：此前确认过的“对方人物 id → 本机人物”，两端人物都还在才有效。按对方人物 id 全局保存（id 是随机 UUID，不同来源不会冲突；同源资料经别的亲戚转手后仍能认回）；只存本机，不进备份、不进共享文件；恢复备份、清空数据时清除。
   3. 同 id：对方人物 id 在本机存在且性别相同 → 同一人；姓名不同记为姓名冲突（不自动改名）。id 相同但性别不同 → 视为无关，对方人物换新 id。
   4. 结构候选：从已认出的人出发，逐层比较父母 / 子女 / 兄弟姐妹 / 配偶。同一位置、同性别、两边在该位置都唯一的一对人列为“可能是同一人”：同名的直接列出；不同名的（如一边写“妈妈”、一边写真名）也列出，并标注“名字不同”。候选须用户勾选确认才合并，否则按新人物处理。
   5. 任一新人物都可以手动指认为“就是本机的某人”（须同性别）。
2. **只补不删**：
   - 新人物：全部加入（不是“我”）。
   - 关系：只新增，端点按认人结果改写；与本机重复的跳过。
   - 手机号：按（人，号码）去重补充，比较时忽略空格、短横线和括号；本机已有主号码的人，补上的号码不设为主号码。
   - 重要日期：本机缺的类型补上；同类型不同值记为冲突。新加入的日期带上文件里的提醒偏好，文件里没有的按默认开启补建，与手工录入一致。忌日只加给合并后已故的人；结婚纪念日按夫妻算一条——夫妻任一方本机已有就只比较不新增，合并后没有配偶的不加。
   - 头像：新人物带上头像；已认出的人本机没有头像时补上，本机有则保留。不覆盖、不删除本机任何头像文件。
   - 本机有、对方没有的人和关系一律保留：对方没有不等于删除。
3. **冲突逐条选择**：姓名不同、在世状态不同（“我”除外）、同类型日期不同的，在预览里逐条显示两边的值，默认“保留我的”，可改选“用对方的”；只有用户改选的才改写本机。
4. **不参与合并**：家庭事项、人情往来、保单（即使文件里带了也不合并）；接收方的设置、联系记录、自定义称呼不变；已认出的人保持本机的提醒偏好。
5. **原子与幂等**：合并结果与对应关系在同一个数据库事务写入，失败整体回滚；重复接收同一份文件不产生任何写入（预览显示“没有新内容”）。

### 16.6 关系约束（合并前校验）

手工录入的约束同样适用于合并结果：每人最多两位父母、最多一位配偶；两人之间只能有一条关系；不能形成辈分循环（不能成为自己的祖先）。合并时另加一条：同一性别的父母最多一位（重复录入同一个人最典型的后果就是“两位母亲”；继亲、收养暂不支持）。两人之间已有完全相同的关系直接跳过，不算矛盾。

- 合并计划在内存中把对方关系逐条加到本机关系图上，违反约束的关系不写入，列入“关系矛盾”清单（谁和谁、对方记的是什么、本机已有什么），用户合并后可以自己到人物页调整。
- 某个候选若不确认、按新人物处理就会造成矛盾（例如不确认对方的“外婆”是同一人，妈妈就会多出一位母亲），在候选旁提示“不合并会产生关系矛盾”，仍由用户决定；产生的矛盾关系按上一条处理，不写入。
- 碰一碰合并（第 10 节）同样经过这一校验。

### 16.7 合并预览

- 分组显示：新增家人（N 位，可展开）；补充内容（N 个手机号、N 个日期、N 张头像）；可能是同一人（勾选）；冲突（逐条选择）；关系矛盾（只读，说明不会写入）。
- 没有任何变化时显示“没有新内容”，不写入。
- 确认后回到家庭页，提示“已合并：新增 N 位家人……”。

### 16.8 不做的事

- 不做自动或实时同步（家庭资料不经服务器）：界面叫“接收家人更新”，不叫“同步”。
- 不同步删除，不做历史版本：长期采用“只补不删、默认保留本机、冲突逐条选择”。
- 碰一碰的夫妻校验、结婚动画不用于其他亲属。

### 16.9 一屏录入核心家人

- 一屏表单按身份分行：父亲、母亲、配偶各一行（已有的不再出现），哥哥 / 姐姐 / 弟弟 / 妹妹、儿子 / 女儿可以加行；每行只填姓名，性别由身份决定，生日和电话以后再补。
- 一次保存，同一事务写入，逐条经过与手工录入相同的关系校验，任一失败整体回滚并指出是哪一行。
- 行内可从通讯录带出姓名和号码；关系仍由所在的行决定，不从通讯录推断。
- 不做表格模板导入；语音输入用输入法自带的功能。
- 兄弟姐妹的血缘处理、父母是否同时记为夫妻等细节，在第 4 批实现前按现有“血缘细分”规则（DEVELOPMENT_PLAN 2.14）补充到本节。

## 17. 家庭协作（确认版与反复补充）

设计要点（原引用的 `docs/handoffs/2026-10-13-family-usability-implementation.md` 第 5 节从未入库，按落地实现回写）：

- 一个协作系列有一位「汇总者」和若干「成员」：汇总者整理后发布「确认版」，成员以收到的确认版为基准补充后「发回补充」。
- 每次发布带版本链与基准快照；接收方以已接受的基准为准做三方比较（基准 / 对方 / 本机），字段、身份、再现人物逐项裁决；本机未汇入的改动单独列出，由用户选择保留或放弃。
- 协作包复用备份 ZIP 格式，只含家人档案，事项 / 人情 / 保单 / 备注不外发。
- 接收前先落「保护副本」，汇入失败或不满意可整库回滚；协作暂存与密钥不进备份。
- 「仅本机保留」人物默认不进关系图与整份分享，确认版再纳入时原位恢复。

本节以下记录落地事实。

### 实现说明（家庭协作改版 阶段 C）

- **规范化快照** `domain/merge/FamilySnapshot.kt`：名册以规范 id（`canon:` 前缀）为键，字段/电话/日期/关系经规范化比较，内容哈希供版本链与幂等核对；仅本机人物不进规范名册。

- **测试**：`FamilyRevisionPlanTest`（19 例）、`MigrationTest` v11→v12、`CollabRoundTripTest`（13 例双设备往返：首次绑定/补充往返/幂等/串系列拒绝/未汇入保护/仅本机排除/私人引用保留/新人物条目/放弃补充）；截图 `collab_connect`/`collab_review_confirmed{,_lg}`/`collab_review_contribution`。
