# 家人侠 亲属关系推导引擎设计

版本：V0.3  
日期：2026-10-02  
项目名称：家人侠  
文档类型：Kinship Engine

> V0.1 实现阶段的补充决策见 DEVELOPMENT_PLAN.md 第 2 节；与本文冲突时，以该节为准。

---

## 1. 文档目的

本文档用于定义“家人侠”如何根据 Person 和 Relationship 组成的关系网络，推导一个人物相对于观察者的亲属关系和称谓。

本文件重点解决：

- 如何从基础关系推导亲属关系
- 如何区分结构关系和展示称谓
- 信息不足时如何处理
- 哪些关系属于 V0.1 推导范围
- 如何避免错误猜测
- 如何为未来地区称谓和自定义称呼留出扩展空间

本文档不负责：

- 数据库表设计
- Android UI 实现
- Room Entity
- 具体图算法代码
- 地区方言称谓全集

---

## 2. 核心原则

家人侠亲属关系推导必须遵守以下原则。

### 2.1 关系事实优先

系统首先计算人物之间真实存在的关系路径。

例如：

```text
SELF
→ PARENT
→ PARENT
```

首先得到结构关系：

父母的父母

随后再结合：

- 中间人物性别
- 目标人物性别
- 家庭分支

得到更具体的称谓。

信息不足时宁可给出“结构关系”，也绝不能猜错称呼。

比如只知道：

我 → 父亲 → SIBLING → 男性

但不知道这个男性比父亲大还是小，就不能猜“伯父”或“叔叔”，只能先显示：

父亲的兄弟

---

### 2.2 不猜测

如果现有数据不足以确定具体称谓，系统不得自行猜测。

例如：

SELF  
→ PARENT（男性）  
→ SIBLING（男性）

只能确定：

父亲的兄弟

如果不知道目标人物和父亲之间谁年龄更大，则不能直接判断：

伯父

或者：

叔叔

此时应展示较宽泛但正确的结构关系。

---

### 2.3 结构关系和称谓分离

亲属关系推导至少分成以下两个层级：

结构关系

例如：

父亲的哥哥

标准称谓

例如：

伯父

未来还可以增加第三层：

家庭自定义称呼

例如：

大伯

因此，系统不应该只保存或返回一个单独的“称呼字符串”。

---

- observer

- relationshipPath

## 4. SELF

SELF 表示：

**当前关系计算的观察者 / 起点人物。**

例如：

SELF  
→ PARENT

表示：

当前观察者的父母之一。

SELF：

- 不是 Relationship 类型
- 不保存到数据库
- 不创建实体
- 默认可以对应 isSelf = true 的 Person
- 未来也可以允许用户选择任意人物作为观察者

路径中的“→ 关系类型 →”表示从观察者出发、沿该关系类型到达下一个人物。

Relationship 的存储方向为：

sourcePerson → type → targetPerson

例如：

A PARENT B

表示 A 是 B 的父母。

---

## 5. 基础关系类型

亲属推导只能基于 DOMAIN_MODEL 中已经确定的基础关系：

- PARENT
- CHILD
- SPOUSE
- SIBLING

不能为了方便推导新增：

- FATHER
- MOTHER
- GRANDFATHER
- UNCLE
- AUNT
- 岳父
- 伯父

等底层关系类型。

这些属于推导结果，而不是底层事实关系。

---

## 6. 性别信息

V0.1 中 Person.gender 为必填。

亲属关系推导可以使用性别决定部分称谓。

例如：

SELF  
→ PARENT

目标人物为男性：

父亲

目标人物为女性：

母亲

再例如：

SELF  
→ CHILD

目标人物为男性：

儿子

目标人物为女性：

女儿

系统不得根据姓名、头像或其他信息猜测性别。

---

## 7. 长幼信息

部分中文称谓不仅依赖性别，还依赖长幼关系。

例如：

父亲的男性兄弟：

- 比父亲年长 → 伯父
- 比父亲年幼 → 叔叔

兄弟姐妹：

- 比 SELF 年长的男性 → 哥哥
- 比 SELF 年幼的男性 → 弟弟
- 比 SELF 年长的女性 → 姐姐
- 比 SELF 年幼的女性 → 妹妹

V0.1 长幼判断来源按以下优先级：

1. 双方 ImportantDate（type = BIRTHDAY）信息完整且可比较时，根据生日判断长幼
2. 生日无法比较，但 SIBLING 关系上存在明确 relativeAgeOrder（非 NULL）时，使用该值
3. 两者都无法确定时（包括 relativeAgeOrder = NULL），降级为宽泛结构关系，不猜测

relativeAgeOrder 的语义为“source 相对于 target 的长幼关系”，仅用于 SIBLING 关系，详见 DOMAIN_MODEL。

本文档中出现的 birthday，指从 ImportantDate（type = BIRTHDAY）读取出的生日信息；Person 本身没有独立的 birthday 字段。

relativeAgeOrder 不是生日的替代品；生日仍然用于生日提醒等其他功能。

如果生日信息缺失、relativeAgeOrder 为 NULL 或无法可靠比较，则不得猜测。

此时应退化为：

- 兄弟
- 姐妹
- 兄弟姐妹
- 父亲的兄弟

等结构描述。

---

## 8. 推导优先级

推导时建议按照以下顺序处理：

1. 找到 observer 到 target 的有效关系路径
2. 判断路径长度
3. 判断每一层 Relationship 类型
4. 读取相关人物性别
5. 如果需要判断长幼，按第 7 节优先级读取生日信息（ImportantDate, type = BIRTHDAY）或 SIBLING.relativeAgeOrder
6. 生成结构关系
7. 如果信息充分，生成标准称谓
8. 如果用户存在 customTitle，则未来优先展示 customTitle

## 18. 信息不足时的降级策略

这是亲属关系引擎最重要的规则之一。

如果不能确定具体称谓：

必须返回能够确定的最具体结构关系。

例如：

已知：

SELF  
→ 父亲  
→ SIBLING  
→ 男性人物

但不知道长幼。

错误：

叔叔

正确：

父亲的兄弟

再例如：

已知：

SELF  
→ PARENT  
→ PARENT

但中间人物信息异常或无法确定分支。

可以返回：

父母的父母

而不是猜“爷爷”或“姥爷”。

## 19. missingInformation

当无法得到更精确称谓时，可以记录缺失的信息。

例如：

missingInformation:

- SIBLING_AGE_ORDER

表示：

如果知道兄弟姐妹之间的长幼关系，就可以进一步确定称谓。

未来 UI 可以提示：

补充他和爸爸的年龄关系，可以判断是伯父还是叔叔。

V0.1 可以暂不实现这种提示 UI，但引擎设计应允许返回缺失原因。

---

## 20. confidence

推导结果可以包含 confidence。

但这里的 confidence 不是 AI 概率。

它表示规则是否得到完整满足。

例如：

EXACT

所有必要信息完整。

结果：

父亲的哥哥  
→ 伯父

PARTIAL

关系路径明确，但缺失部分信息。

结果：

父亲的兄弟

V0.1 可以直接使用：

- EXACT
- PARTIAL

两种状态。

## 21. 多路径问题

真实家庭关系网络中，一个人物可能通过多条路径到达。

例如复杂姻亲、再婚家庭可能出现：

A → B → C

以及：

A → D → C

V0.1 暂不完整解决复杂多路径选择问题。

原则：

- 优先使用最短有效关系路径
- 如果存在多个同长度且含义冲突的路径，不应静默选择一个错误结果
- 后续版本可以增加路径优先级和冲突检测

---

## 22. 循环关系保护

亲属关系网络理论上可能因为错误录入产生循环。

例如：

A PARENT B  
B PARENT A

DOMAIN_MODEL 已要求避免明显冲突。

Kinship Engine 在遍历关系网络时仍应具备循环保护。

例如：

- 已访问 Person 集合
- 最大路径深度

V0.1 不需要在本文件规定具体算法参数。

---

## 23. 最大推导深度

V0.1 主要处理一级和二级关系。

因此关系推导不需要无限搜索整个家庭图。

产品目标不是一次性解决所有中国亲属关系。

后续版本再逐步扩大推导深度。

V0.3 起最大推导深度为 5 步（例如“妻子的父亲的堂弟”正好 5 步），超过 5 步的人物视为未关联。

## 33. V0.1 引擎设计原则

正确优先于具体

宁可显示：

父亲的兄弟

也不要错误显示：

叔叔

关系事实优先于中文称谓

先理解“他是谁”，再决定“应该叫什么”。

不猜测

任何依赖缺失信息的结论，都必须降级。

可解释

系统应该尽量能够告诉用户：

为什么这个人是我的伯父。

例如：

他是你父亲的哥哥。

地区差异可扩展

不要把单一地区习惯永久写死进核心关系模型。

自定义称呼优先

未来支持家庭自己的真实叫法。

## 36. 长幼顺序补充说明

早期版本中“长幼顺序 / relativeAgeOrder”曾是领域模型缺口：生日可空，导致“知道长幼但不知道准确生日”的情况无法表达。

该问题已通过 SIBLING 关系上的可选 relativeAgeOrder 解决。

用户不需要知道准确生日，也可以记录：

“他比我爸爸大。”

从而使伯父等长幼称谓仍然可以被正确推导。

### 38.1 通用约定

- 选词原则：有通行口语叫法的用口语（如姑奶奶、舅姥爷），口语因地区而异或要靠排行区分的用书面称谓（如伯祖父、曾外祖父）。地区差异由自定义称呼覆盖显示。
- 长幼判断：
  - 经显式或隐式 SIBLING 的一步（如“爷爷的哥哥”），与第 7 节相同：先比生日，再看该 SIBLING 记录的 relativeAgeOrder；无法判断记 `SIBLING_AGE_ORDER`。

### 38.3 随配偶称

配偶一侧的亲属，按配偶对他的称谓称呼（例如妻子的父亲的弟弟，妻子叫叔叔，我也叫叔叔）。

- 适用路径：SPOUSE 之后的子路径 P 以 PARENT 或 SIBLING 开头，且 P 不是单独的 PARENT、单独的 SIBLING。这两种仍用第 13 节（岳父 / 岳母 / 公公 / 婆婆）和 37.2（大舅子 / 小姨子 / 大伯子 / 小姑子等）。
- SPOUSE → SIBLING → SPOUSE：先按 37.2 判断连襟 / 妯娌；不符合时（如妻子的哥哥的妻子、丈夫的姐姐的丈夫）按随配偶称。
- 推导方式：以配偶为观察者、对子路径 P 套用本文全部规则。若结果为 DERIVED，则：
  - standardTitle、confidence、missingInformation 取配偶视角的结果；
  - kind = DERIVED；
  - structuralDescription = `妻子 / 丈夫` + `的` + 配偶视角的结构关系。
  若配偶视角为 STRUCTURAL，则按普通结构关系逐层拼接。
- 长幼一律相对配偶判断（例如“妻子的表哥”指比妻子大的表兄）。
- 不适用：SPOUSE → CHILD 开头（配偶的子女未记为我的子女，属继亲）、SPOUSE → SPOUSE 开头。

示例（我为男，妻子为女）：

| 结构关系 | 标准称谓 |
|---|---|
| 妻子的父亲的弟弟 | 叔叔 |
| 妻子的父亲的哥哥 | 伯父 |
| 妻子的父亲的姐妹 | 姑姑 |
| 妻子的母亲的兄弟 / 姐妹 | 舅舅 / 姨妈 |
| 妻子的父亲的父亲 / 母亲 | 爷爷 / 奶奶 |
| 妻子的母亲的父亲 / 母亲 | 姥爷 / 姥姥 |
| 妻子的父亲的弟弟的妻子 | 婶婶 |
| 妻子的父亲的哥哥的儿子（比妻子大） | 堂哥 |
| 妻子的父亲的堂弟（5 步：SPOUSE → PARENT → PARENT → SIBLING → CHILD） | 堂叔 |
| 妻子的哥哥的儿子 | 侄子 |
| 妻子的姐姐的女儿 | 外甥女 |
| 妻子的哥哥的妻子 | 嫂子 |

我为女时同理：丈夫的父亲的弟弟 → 叔叔，丈夫的姐姐的丈夫 → 姐夫。

### 38.4 对第 37 节的改动

- SPOUSE → SIBLING → SPOUSE 中不是连襟 / 妯娌的组合，由“standardTitle 为空”改为按 38.3 随配偶称。
- 其余 37.2 规则不变。

### 38.5 仍不推导（按 STRUCTURAL 逐层描述）

- 继亲：PARENT → SPOUSE（父母的配偶）、SPOUSE → CHILD（配偶的子女）。数据里没有记“他是我的父亲 / 母亲 / 子女”，并不能证明真的不是（可能只是漏记），直接标“继母”“继子”属于猜测。
- 高祖、玄孙及更远的直系。
- 父母的堂表兄弟姐妹的子女（再从兄弟姐妹）、曾祖辈的兄弟姐妹。
- 兄弟姐妹配偶的亲属（如嫂子的父母）、子女配偶的兄弟姐妹等，没有通行的固定称谓。

## 40. 申报堂表亲（COUSIN 记录）

用户在“添加关系 / 添加家人”里选择“堂兄弟 / 表兄弟”等堂表亲缘时，
除挂接中间人父母边外，还在两人之间写入一条 type = COUSIN 的关系记录
（DATABASE_SCHEMA 7.18），携带所申报的长幼（relativeAgeOrder，可空）。

### 40.1 语义与限制

- COUSIN 是**对称的申报记录**：只断言“两人是堂/表亲（+申报长幼）”，
  不含中间链条信息，因此**不参与普通路径遍历**（邻接不建可遍历边），
  也不会让引擎把堂表亲误认成亲兄妹。
- 堂表亲长幼判断顺序（37.1 / 38.1 / 38.2 E·G 共用）：
  1. 两人间申报 COUSIN 记录的 relativeAgeOrder
     （source 相对 target，方向随查询端翻转，同 SIBLING）；
  2. 双方完整生日（完整且同一天 → SAME）；
  3. 无法判断 → `BIRTH_DATES`。
- 申报记录只作长幼依据，不区分堂 / 表：堂表仍由真实路径
  （PARENT → SIBLING → CHILD 上两人的性别）判定。

### 40.2 无真实路径时的兜底结果

两人间只有申报 COUSIN 记录、不存在普通路径时，resolve 返回
kind = DERIVED 的单步结果（relationshipPath = [COUSIN]）：

- 申报长幼明确：standardTitle 为“堂表哥 / 堂表弟 / 堂表姐 / 堂表妹”，
  EXACT；结构关系为“堂表亲（兄弟 / 姐妹）”。
- 长幼未申报且生日不可比：standardTitle 为“堂表兄弟 / 堂表姐妹”，
  PARTIAL，missingInformation = `BIRTH_DATES`。
- directRelationLabel 对 COUSIN 记录同样按申报长幼给
  “堂表哥 / 堂表弟 / 堂表姐妹”等标签。

### 40.3 分代

generations() 把申报 COUSIN 视为同代连接：无其他路径的申报堂表亲
落到与观察者同一代（0 代方向展开），不再计入“未关联”。
