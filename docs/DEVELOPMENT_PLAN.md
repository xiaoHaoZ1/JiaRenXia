## 2. V0.1 实现决策

### 2.1 工程结构

物理模块只有三个：

- `:app`：Android 应用。数据层、提醒、各页面按包划分（data / reminder / feature.* / ui / navigation），对应 ARCHITECTURE 第 9 节的逻辑边界。
- `:core:model`：领域模型，纯 Kotlin，不依赖 Android。
- `:core:kinship`：称谓推导引擎，纯 Kotlin，只依赖 `:core:model`。

其他约定：

- 包名 / applicationId：`com.jiarenxia.app`（2026-10-07 更名，原为 `io.github.xiaohaoz1.jiarenxia`；Kotlin namespace 不变仍为 `io.github.xiaohaoz1.jiarenxia`）。
- minSdk 26，compileSdk / targetSdk 36。
- 数据层不拆成五个 Repository：所有家庭数据的读写集中在 `FamilyRepository`，跨表写操作在其内部用 Room 事务完成（解决审计 P1-10）。另有 `SettingsRepository`（DataStore）、`AvatarStorage`（头像文件）、`ReminderScheduler`（提醒调度）。
- 不引入图片加载库和网络库。合并后的 Manifest 中不得出现 `android.permission.INTERNET`。

### 2.2 家庭页与人物入口（审计 P1-1）

家庭页（首页）只展示已经存在的人物，不显示空占位，分三块：

1. **我**
2. **核心家人**：从“我”出发的最短关系路径属于以下五种之一的人物：
   - PARENT（父母）
   - PARENT → PARENT（祖辈）
   - SPOUSE（配偶）
   - CHILD（子女）
   - SPOUSE → PARENT（配偶父母）

   排列顺序：父母 → 祖辈 → 配偶 → 子女 → 配偶父母。同组内男性在前；子女按生日从大到小，没有可比较生日的按创建时间排。
3. **其他家人**：其余所有人物，包括兄弟姐妹、伯叔姑舅姨、超出 V0.1 称谓表的亲属，以及与“我”没有关系路径的人物（标注“未关联到我”）。有路径的按路径长度、再按姓名排序；未关联的排在最后。

其他决定：

- 家庭页右下角“添加家人”按钮进入添加家人页（见 2.3）。
- **搜索纳入 V0.1**：按姓名、显示称谓、结构关系做包含匹配（落实 VISION 9.6、场景五）。
- “被用户标记为重要的家人”不进入 V0.1，没有对应字段。

### 2.3 新增人物与关系管理（审计 P1-2、P1-3、P1-4）

**一、新增人物必须带一条关系。** 新增人物时，必须指定一位已有人物作为“关联人”（默认是“我”），并选择“新人物是关联人的什么人”。人物和这条关系在同一个事务中创建。

**二、关系选项。** 选项与存储方式对照如下（source / target 即数据库的 source_person_id / target_person_id）：

| 选项 | 存储的关系 | 新人物性别（预填） | relativeAgeOrder |
|---|---|---|---|
| 父亲 / 母亲 | 新人物 PARENT 关联人 | 男 / 女 | NULL |
| 儿子 / 女儿 | 关联人 PARENT 新人物 | 男 / 女 | NULL |
| 丈夫 / 妻子 | 新人物 SPOUSE 关联人 | 男 / 女 | NULL |
| 哥哥 / 姐姐 | 新人物 SIBLING 关联人 | 男 / 女 | OLDER |
| 弟弟 / 妹妹 | 新人物 SIBLING 关联人 | 男 / 女 | YOUNGER |
| 兄弟（长幼未知）/ 姐妹（长幼未知） | 新人物 SIBLING 关联人 | 男 / 女 | NULL |

- 选项中包含的性别，是用户明确给出的信息，不属于“系统猜测性别”。表单中性别仍可修改；修改后，已存关系的类型不变，称谓按保存的性别重新推导。

**三、快捷入口。** 引导流程和添加家人页提供以下快捷入口：

| 入口 | 关联人 | 选项 |
|---|---|---|
| 父亲 / 母亲 | 我 | 父亲 / 母亲 |
| 配偶 | 我 | 丈夫 / 妻子 |
| 子女 | 我 | 儿子 / 女儿 |
| 兄弟姐妹 | 我 | 哥哥 / 弟弟 / 姐姐 / 妹妹 / 长幼未知 |
| 爷爷 / 奶奶 | 父亲 | 父亲 / 母亲 |
| 姥爷 / 姥姥 | 母亲 | 父亲 / 母亲 |
| 配偶的父亲 / 配偶的母亲（按性别显示为岳父岳母或公公婆婆） | 配偶 | 父亲 / 母亲 |
| 其他亲属 | 任选已有人物 | 任选上表选项 |

- **前置条件**：爷爷 / 奶奶需要先有父亲，姥爷 / 姥姥需要先有母亲，配偶父母需要先有配偶。前置人物不存在时，入口置灰，提示“请先添加父亲”等，并提供直接添加的按钮。
- 父亲 / 母亲已故或情况不详时，用户仍然新建这个人物（姓名可以直接写“父亲”），需要时标记为已故。V0.1 不设占位人物类型。
- 已经存在的父亲 / 母亲 / 配偶不再显示对应入口。若关联人有两位同性别父母，由用户选择具体的关联人。

**三之一、更多亲戚（V0.3）。** 添加家人页（不含首次引导）在上表之后增加“更多亲戚”分区，“其他亲属”始终排在最后（首次引导也保留）。关联人按与“我”的关系路径自动定位；只有一位时直接关联，多位时由用户选择；没有时入口置灰并提示前置人物。

| 入口 | 关联人（与“我”的关系路径） | 选项 | 没有关联人时的提示 |
|---|---|---|---|
| 伯叔姑 | 父亲 | 兄弟姐妹六项 | 请先添加父亲（可直接添加） |
| 舅舅姨妈 | 母亲 | 兄弟姐妹六项 | 请先添加母亲（可直接添加） |
| 堂表兄弟姐妹 | 父母的兄弟姐妹 | 儿子 / 女儿 | 请先添加伯叔姑或舅舅姨妈 |
| 侄子外甥 | 兄弟姐妹 | 儿子 / 女儿 | 请先添加兄弟姐妹（可直接添加） |
| 儿媳女婿 | 子女 | 丈夫 / 妻子 | 请先添加子女（可直接添加） |
| 孙辈 | 子女 | 儿子 / 女儿 | 请先添加子女（可直接添加） |
| 祖辈的兄弟姐妹 | 祖辈 | 兄弟姐妹六项 | 请先添加爷爷奶奶或姥爷姥姥 |
| 父母的堂表亲 | 祖辈的兄弟姐妹 | 儿子 / 女儿 | 请先添加祖辈的兄弟姐妹 |
| 配偶的兄弟姐妹 | 配偶 | 兄弟姐妹六项 | 请先添加配偶（可直接添加） |
| 配偶的叔伯姑姨 | 配偶的父母 | 兄弟姐妹六项 | 请先添加配偶的父母 / 配偶（可直接添加） |

“兄弟姐妹六项”即哥哥、弟弟、姐姐、妹妹、兄弟（长幼未知）、姐妹（长幼未知）。

**四、不自动补建关系。** 系统不自动创建用户没有说出的关系，例如父亲与母亲的 SPOUSE、配偶与子女的 PARENT。用户可以随后通过“添加关系”补充。

**五、人物详情页的“关系”区块。** 列出该人物全部直接关系，从该人物视角显示，例如“父亲：杨福生”“哥哥：杨建春”。

- 每条关系可以删除，需要二次确认。
- SIBLING 关系可以修改长幼：年长 / 年幼 / 相同 / 未记录。
- “添加关系”：把当前人物与另一位已有人物连接起来，选项同上表。
- 删除关系后，可能有人物与“我”失去路径。这些人物仍然出现在家庭页“其他家人”中，标注“未关联到我”，不会丢失。

**六、关系校验。** 由 FamilyRepository 在写入事务中执行：

1. 两端人物都存在，且不是同一人物。
2. 任意两人之间最多一条直接关系，不论类型、不论方向。这条规则同时覆盖完全重复、正反重复，以及“A 是 B 的父母，同时 B 是 A 的父母”这类矛盾。
3. 每个人最多两位父母。
4. 每个人最多一位配偶。V0.1 没有婚姻历史和状态，再婚、前任属于后续版本。
5. 不允许祖先循环：如果 Y 已经是 X 的祖先，则拒绝写入 X PARENT Y。
6. relativeAgeOrder 只能出现在 SIBLING 上。

违反校验时返回明确的错误类型，界面显示中文提示。

**七、存储方向。** SIBLING / SPOUSE 不做规范化排序，按创建时的方向存储：source 为新人物或“另一位”人物，target 为关联人；relativeAgeOrder 表示 source 相对 target。

- 正反重复由第六条第 2 点保证，因此 DATABASE_SCHEMA 7.13 中可选的规范顺序不采用。
- 读取时的视角翻转（DATABASE_SCHEMA 第 18 节）照常执行。

### 2.4 称谓推导补充规则（审计 P1-5）

**一、推导结果的结构。** 推导结果 KinshipResult 在 KINSHIP_ENGINE 第 28 节的基础上增加 `kind`：

| kind | 含义 | structuralDescription | standardTitle | confidence | missingInformation |
|---|---|---|---|---|---|
| SELF | 目标就是观察者 | 我 | 我 | EXACT | 空 |
| DERIVED | 路径命中 V0.1 称谓规则（KINSHIP 第 9–15 节） | 规则中的结构关系 | 规则结果，可能为空 | EXACT / PARTIAL | 视情况 |
| STRUCTURAL | 有路径，但不在 V0.1 称谓规则内 | 逐层拼接，例如“哥哥的妻子” | 空 | EXACT | 空 |
| UNRELATED | 在最大深度内找不到路径 | 未关联到我 | 空 | PARTIAL | NO_PATH |

- customTitle 在 V0.1 中恒为空。
- PARTIAL 只表示“信息缺失”。“超出规则范围”用 STRUCTURAL 表达，不混用。

**二、逐层拼接的规则。** 每一步的标签：

- PARENT → 父亲 / 母亲
- CHILD → 儿子 / 女儿
- SPOUSE → 丈夫 / 妻子
- SIBLING → 长幼可确定时用哥哥 / 弟弟 / 姐姐 / 妹妹，否则用兄弟 / 姐妹

各步之间用“的”连接。

**三、长幼判断。** 判断兄弟姐妹 Y 相对 X 的长幼，按以下顺序：

1. 双方生日都有年、月、日，且日期不同：按生日判断。
2. 否则，如果两人之间存在显式 SIBLING 关系，且 relativeAgeOrder 不为 NULL：使用它。当 X 是该关系的 source 时，需要取反。
3. 否则无法确定。

判断结果对应的输出：

| 结果 | 输出 |
|---|---|
| OLDER / YOUNGER | 哥哥、弟弟、伯父、叔叔等具体称谓 |
| SAME | 不给长幼称谓：structuralDescription 为“兄弟”“姐妹”“父亲的兄弟”等；standardTitle 为空；confidence = EXACT；missingInformation 为空（不提示补充） |
| 无法确定 | standardTitle 为空；confidence = PARTIAL；missingInformation = SIBLING_AGE_ORDER |

- 双方生日完整且同一天、又没有 relativeAgeOrder，按“无法确定”处理。双胞胎仍然可以通过 relativeAgeOrder 指定先后。

**四、隐式兄弟姐妹。** 两个不同人物只要有至少一位共同父母，在路径搜索中就视为兄弟姐妹。

- 这种隐式关系只能用生日判断长幼。
- 同一对人之间若有显式 SIBLING，以显式关系为准。
- 因此，伯父被录成“爷爷的儿子”时，仍然能按 SELF → PARENT → SIBLING 识别。

**五、路径搜索。**

- 在 PARENT（向上）、CHILD（向下）、SPOUSE、SIBLING（含隐式）组成的图上做广度优先搜索，最大深度 4（V0.3 起为 5，见 KINSHIP_ENGINE 第 23、38 节），用已访问集合防止循环。
- 存在多条最短路径时，优先级为：DERIVED 且 EXACT > DERIVED 且 PARTIAL > STRUCTURAL。
- 若多条最短路径给出不同的非空 standardTitle，standardTitle 置空，structuralDescription 取顺序上第一条路径的结果，不静默选一个可能错误的称谓。

**六、同性别配偶。** 配偶双方性别相同时，按 KINSHIP 13.3 返回“配偶的父亲 / 配偶的母亲”（V0.3 起按配偶性别写作“丈夫的父亲”“妻子的母亲”等）：kind = DERIVED，standardTitle 为空，confidence = EXACT。

**七、界面显示规则。**

- 显示称谓 = customTitle ?: standardTitle ?: structuralDescription。
- 详情页在显示称谓与结构关系不同时，同时显示结构关系作为解释。
- 若 missingInformation 包含 SIBLING_AGE_ORDER，显示提示：“补充长幼信息后，可以确定具体称谓”。

### 2.5 生日与提醒（审计 P1-6、P1-9 及 P2）

**一、生日录入。**

- 年份可选，提供“不知道出生年份”开关；月、日必填。
- 有年份时，必须是真实存在的日期。没有年份时，允许 2 月 29 日。

**二、生日与提醒偏好的数据操作。**

- 创建生日时，在同一事务中创建 ReminderPreference（enabled = true）和提前天数 {0, 1}。
- 修改生日时，原地更新 ImportantDate，保留其提醒设置。
- 清除生日时，删除该行，提醒偏好随之级联删除。

**三、开关。**

- 人物详情页的“生日提醒”开关切换 enabled。
- 偏好不存在时视为不提醒；打开开关时补建偏好，提前天数为 {0, 1}。
- “我的”页面有“生日提醒总开关”，保存在 DataStore，默认开启。

**四、提醒时间。**

- 三类提醒（生日与纪念日 / 家庭事项 / 联系）各有一个每日检查时刻，默认 09:00（本地时间），在“我的 → 提醒”各行分别设置，均随备份导出；下文的“09:00”均指各类所设时间。
- 提前天数 0 表示当天提醒，1 表示提前一天提醒。
- 2 月 29 日的生日在平年按 2 月 28 日处理，显示和提醒都如此。

**五、已故人物。** 不发生日通知，也不出现在提醒页。生日和提醒偏好继续保存；状态改回在世后，提醒自动恢复。

**六、调度方式。**

- 只排一个唯一的一次性 WorkManager 任务，目标时间是最近的下一个已开启提醒时刻。
- 任务运行时读取数据库，按各自时刻门槛发出当天到期且当天尚未通知过的提醒，在 DataStore 中记录运行日期与已通知键集合，然后安排下一次运行。
- `reconcile()` 在以下时机调用：应用启动、人物 / 生日 / 纪念日 / 事项 / 联系计划与记录 / 提醒开关与时刻发生变化、任务运行结束时。有任一已开启时刻今天已过则立即补跑一次——数据在时刻过后被改成“今天到期”时仍能当天提醒，已通知过的靠当天键集合去重。
- 数据库是唯一事实来源：任务运行时才读数据，所以删除人物、清除生日或关闭提醒之后不会残留提醒，也不需要逐人取消闹钟。
- 允许非精确送达，不申请精确闹钟权限。

**七、通知。**

- 渠道名“生日提醒”。
- 文案：“今天是 {显示称谓} {姓名} 的生日”，或“明天是 {显示称谓} {姓名} 的生日”。
- 点击打开该人物详情页。
- 锁屏可见性为 PRIVATE，公开版本显示“家人侠：有家人的生日提醒”。

**八、通知权限（Android 13+）。**

- 用户第一次保存生日或打开提醒开关时，先说明用途，再申请权限。
- 被拒绝后，提醒页显示提示条，并提供前往系统设置的按钮。

**九、提醒页。**

- 内容：今天生日、即将生日（未来 30 天内，按剩余天数排序）。每项显示姓名、显示称谓、日期和剩余天数，点击进入详情。
- 总开关关闭时，显示“生日提醒已关闭”提示条。

**十、年龄。** V0.1 不计算年龄（PRD 7.4）。

**十一、双生日（数据库第 8 版起）。**

- 每人最多一个阳历生日、一个农历生日（`BIRTHDAY_SOLAR` / `BIRTHDAY_LUNAR`
  各占一个槽位），分别编辑与删除；年份依旧可未知。
- 编辑页完整日期提供用户主动触发的历法换算填充，不在打开页面时
  偷偷保存第二份；缺少年份时也不生成看似准确的对应出生日期。
- 两份完整生日换算出的公历不一致时界面提示核对，不自动覆盖。
- 提醒完全独立：两个槽位可各自开关、各自设提前天数；
  补记第二份生日时新提醒默认关闭，原配置保留。
- 通知与时间线按人聚合：阳历、农历生日落在同一天时合并为一条，
  文案说明“阳历和农历同一天”；不同目标日同一发送日也合并为一条、
  分号列出各历法生日，不丢内容也不重复发。
- 年龄与长幼只用可确定的真实出生日：两份完整生日一致时采用；
  冲突时判未知不猜；都无年份同样未知。

### 2.6 清空所有数据（审计 P1-7）

- 入口：“我的”→ 数据管理。先给出强提醒，再要求二次确认。
- 清理范围：Room 全部表、DataStore、头像目录、提醒任务、已发出的通知。完成后回到首次引导。
- 是否完成引导，以是否存在 isSelf 人物为唯一判断依据，不另设“已完成初始化”标记。

### 2.7 隐私与备份（审计 P1-8）

- 不声明 INTERNET 权限。
- 系统云备份排除全部数据：Android 12+ 用 `dataExtractionRules` 中的 cloud-backup，Android 11 及以下用 `fullBackupContent`。
- Android 12+ 允许设备间迁移（device-transfer）。这种迁移不经过云端，便于用户换机。
- 日志中不输出姓名、手机号、生日、家庭关系和备注。

### 2.8 手机号（P2）

**一、顺序。** 按录入顺序保存：同一次保存的多个号码，createdAt 依次递增。显示时主号码在前。

**二、去重。**

- 去重时先忽略空格、短横线、括号再比较；保存时仍保留用户的原始输入。
- 数据库层另有 UNIQUE(person_id, number) 兜底。

**三、拨号。**

- 用 ACTION_DIAL 打开系统拨号界面，由用户确认拨出。
- 只使用 ACTIVE 号码。有多个 ACTIVE 号码时弹出选择。

### 2.11 家庭关系图

**一、范围（2026-10-17 改版）。** 以“我的家庭 / 父系 / 母系 / 配偶系 / 配偶父系 / 配偶母系”六个入口限定显示范围，锚点依次为我、父亲、母亲、配偶、配偶父亲、配偶母亲。锚点本人、亲兄弟姐妹、父母、祖父母入图；父母及他们亲兄弟姐妹的各支沿子女向下三代，补齐范围内每人的配偶，但不再沿这些配偶扩展原生家庭。锚点本人及手足的两代后代也保留（父母未录入时仍有效）。因此“我的家庭”到我的孙辈，父系祖辈旁支到我下一辈。未关联人物不入图，远于当前范围的资料仍保存在家庭页。

- 夫妻双方都有原生家庭时，几何上选一条出生家庭作为主树，另一侧真实亲子连线仍保留；不删除关系、不复制人物。

已记录子女位于父母同辈或上辈时，不把该边反转绘制；原始记录保留，关系图提示“亲子关系待核对”，可打开对应人物详情。导出图同样不倒画，并注明待核对数量；不自动改动真实资料。

### 2.16 界面改版（2026-10-09）

起因：常用入口被设置挤走，「我的」页要滚三屏才看得到备份，而「数据」卡里塞了六类用途不同的东西（备份、恢复、分享、两种碰一碰、婚礼祝词、清空）。设计稿源文件在 `docs/design/`（`main.html` 四个主页面、`mine.html` 我的三屏，共用 `base.css`）；`node docs\design\render.mjs` 用本机 Edge 重出 PNG，产物写到不入库的 `runtime/design/`。

**一、主题 token。** 保留品牌砖红 `#B4473C` 作唯一强调色，其余去饱和：背景 `#FBF8F5`、卡片纯白、发丝描边 `#EFE7E1`、次要文字 `#7A6E68`、守护绿 `#2F6B4F`；圆角统一 14dp（原 12/16/20/28）；`JrxCard` 去阴影改描边；`GradientHeader` 改平底（`headerGradientStart` 现在等于背景色，粉色渐变页头取消）。深色方案同样处理。改 token 即全 App 生效。

**二、信息架构。** 按「用户目的」而不是「实现方式」分家：

| 原位置 | 新位置 | 理由 |
|---|---|---|
| 我的 → 提醒（三类开关与时刻） | 家事页顶栏铃铛（`settings/reminders`） | 想改「生日提醒几点」时心里想的是「提醒」，不是「我的」 |
| 我的 → 数据（备份/恢复/清空） | 我的 → 数据管理（`settings/data`） | 只管「给自己留副本」 |
| 我的 → 数据（分享/碰一碰/婚礼祝词） | 家庭页 → 共享与连接（`share/connect`） | 这些是「和家人交换资料」，属于家庭 |
| 我的 → 外观 | 我的 → 外观与字号（`settings/appearance`） | |
| 我的 → 功能模块 | 我的 → 功能管理（`settings/modules`） | |
| 我的 → 隐私说明 / 关于 | 我的 → 帮助与关于（`settings/about`） | 应用锁下线后「隐私与安全」只剩一页静态说明，不值得占一级入口 |

「我的」首屏因此只剩：个人资料行 + 备份卡（带上次备份时间与「备份…」按钮）+ 四个入口 + 一句「资料只留在你的手机里」。二级页共用 `ui/mine/SettingsRows.kt` 的 `SettingsScaffold`/`SettingsGroup`/`SettingsNavRow`/`SettingsSwitchRow`。

**三、几处刻意的取舍。**
- 备份按钮文案是「备份…」并标注「需设置密码」：点下去要输两次密码再选保存位置，一键按钮会骗人。
- 关系图在家庭页保留带缩略图的入口卡，不降成文字链——它是产品招牌能力。
- 守护页主标题改成一句人话摘要（「24 小时没动静，就打电话通知杨帆」），「正在使用手机」降为小字：后者每分钟都在变且父母自己看永远是「正在使用」，信息量为零。
- 家事页的「全部 / 未来 30 天」筛选器**没做**：那是新功能不是换皮，产品规则（筛什么、默认值、与导出范围的关系）要先定。
- 二级页不用插画：特大字号（系统 fontScale × 1.5）下插画会把列表挤出屏幕。
- slogan 不常驻页头，只留给首次使用与空状态。

**四、四批的实际落地。**

① **主题 token + 我的页 + 五个二级页 + 路由**。见上面一、二两节。

② **家庭页**。页头只留标题「家庭」+ 搜索/添加两个按钮；删掉问候语、日期行、本人头像行、三个统计胶囊（`StatPill`）和右下角的「添加家人」FAB（添加入口上移到顶栏 ＋）。关系图从顶栏图标升级为带缩略示意图的入口卡。当天有人过生日时显示生日横幅（含「打个电话」），没有则显示近期生日卡。核心家人从三列大头像九宫格（一屏 6 人）改成两列紧凑行（一屏 8 人，`CoreMemberCard` 已删）：32dp 头像 + 姓名 + 灰色称谓，第二行小字按 已故 → 今天 → N 天后 → N 天未联系 → 生日日期 的优先级只显示一条。「其他家人」行的粉色称谓胶囊也改成右侧灰字。附带删除：`domain/Greeting.kt`（问候语函数已无调用方）、`FamilyUiState.hour`。

### 2.14 称谓录入与血缘细分（减少重复选择已知关系，允许关系不完整）

- 用户视角选称谓，不把称谓翻译成通用关系：兄妹角色按关联人是否是
  “我”的父/母显示为伯叔姑/舅姨（`RelativePlan.roleLabel`），
  性别/分支由称谓预填；但**称呼不推断血缘**——选了“姑姑”不代表
  她是爸爸的亲姐妹，每一层都由用户显式确认。
- 兄妹类角色（六个，含长幼未知 BROTHER/SISTER）在表单内做三级细分
  （`SiblingLineage`）：亲兄弟姐妹 / 堂表兄弟姐妹 / 其他关系只记称呼。
  **默认不预选**（lineage=null）：选了“姑姑”不默认亲兄妹，未确认不能保存。
- 亲兄弟姐妹：`SharedParents`（同父同母/同父/同母/暂不确定）确认
  共享哪些父母；默认未确认（不默认同父同母），用户选定后按确认信息处理，
  未知不补齐为同父同母。只补**已录祖辈**（`RelativePlan.parentCandidates`），
  唯一候选需用户勾选才补建（候选存在不等于确认），多候选必须显式选定
  或“不确定”（不静默关联），未记录的一侧不凭空创建。
- 换关联人、换称谓（含连续添加里换关联人）时血缘确认全部失效重选；
  “保存并继续添加”只保留已确认且仍适用于同一关联人的上下文
  （称呼文本属上一位，不带到下一位）。

## 6. 第二轮实现决策（界面改版、农历生日、通讯录选号、备份恢复、守护迁移）

本节记录 V0.1 之后第二轮开发的决策，范围由用户确认：守护功能合并进同一个 App；界面采用“温馨暖色”风格并默认浅色；同时实现农历生日、通讯录选号与加密备份恢复。

### 6.1 界面改版

- 风格：米白、杏色底，砖红为主色，大圆角卡片与柔和阴影，贴近 BRAND “温暖、克制、可信赖”。
- 主题：默认浅色；“我的 → 外观”可切换浅色 / 深色 / 跟随系统。深色主题使用暖棕色，不使用中性冷灰。不使用系统动态取色。
- 统一的设计组件（卡片、分组标题、渐变头图、日期块、倒计时标签、快捷操作按钮、空状态插画）放在 `ui.designsystem`。所有页面只使用这些组件和主题配色，不在页面里写死颜色。
- 头像占位：按姓名确定性地选取暖色渐变，显示首字。已故人物显示为去色。
- 亲属分支配色：父系用主色，母系用青绿，配偶一方用琥珀色。首页头像外圈与关系图节点使用同一套配色。
- 家庭页按分支分组展示“其他家人”：兄弟姐妹、兄弟姐妹的家庭、父系亲属、母系亲属、配偶的亲属、子女的家庭、未关联到我。

### 6.2 农历生日

- ImportantDate 的 calendarType 增加 LUNAR。数据库 important_dates 新增 `is_leap_month`（整数，默认 0）。数据库版本从 1 升到 2，必须提供 Migration(1, 2) 和迁移测试。
- 农历与公历的换算使用 Android 自带的 `android.icu.util.ChineseCalendar`，不引入第三方库。换算放在 `:app`，纯 Kotlin 模块通过接口使用换算结果。
- 下一次生日的计算规则：
  - 取当前农历年中该月该日对应的公历日期；如果已经过去，取下一农历年。
  - 闰月出生的人，在没有该闰月的年份按同名普通月计算。
  - 出生在三十、而当年该月只有二十九天时，按二十九计算。
- 长幼判断：农历生日有年份时，先换算为公历出生日期再比较；没有年份时不参与比较（与公历规则一致）。
- 显示：“农历 1964年八月十五”或“农历 八月十五（未填年份）”，同时显示下一次对应的公历日期。
- 提醒、近期生日、倒计时都按换算后的公历日期计算。

### 6.3 通讯录选号

- 使用系统联系人选择器选择一个具体号码（`ACTION_PICK` + `CommonDataKinds.Phone.CONTENT_URI`）。系统只临时授权读取所选的那一条，**不申请 READ_CONTACTS 权限**。
- 编辑手机号时可以“从通讯录选择”；新增人物时可以“从通讯录导入”，同时预填姓名和号码，用户仍可修改。

### 6.4 加密备份与恢复

- 入口：“我的 → 数据管理 → 备份到文件 / 从备份恢复”。文件由用户通过系统文件选择器决定保存位置，应用不联网。
- 内容：全部人物、手机号、关系、重要日期、提醒偏好、头像图片，以及外观与提醒总开关设置。不包含守护配置：守护配置属于具体某台手机，换机后需要重新设置。
- 格式：先把 JSON（Android 自带 org.json）与头像打包成 zip，再整体加密。
  - 加密：AES-256-GCM。密钥由用户密码经 PBKDF2-HMAC-SHA256 派生，迭代 600,000 次，随机 16 字节盐、12 字节 IV。
  - 文件头：魔数 `JRXB`、格式版本、迭代次数、盐、IV，之后是密文。
  - 密码至少 6 位，需要输入两次，应用不保存密码。
- 恢复：
  - 校验格式版本，展示内容摘要（人数、关系数等），二次确认后**替换当前全部数据**。V0.2 不做合并。
  - 恢复完成后重新调度提醒。
  - 密码错误或文件损坏时给出明确提示，当前数据不受影响：先在临时位置完整解密、校验，成功后才在一个事务内替换。

### 6.5 守护迁移（来自 GuardMyFather）

**一、模块。** 新增 Android 库模块 `:feature:guardian`（包名 `io.github.xiaohaoz1.jiarenxia.guardian`），原样保留 GuardMyFather 的分层：

- core：纯 Kotlin 状态机、规则、端口接口，用 JVM 测试覆盖。
- data：设备加密存储、事件日志。
- sys：前台服务、闹钟、广播、响铃、拨号、短信、使用情况兜底、厂商设置跳转。
- ui：守护页、设置、权限清单、日志、锁屏确认页。

模块之间的依赖规则：

- 模块内部继续使用自己的轻量 ServiceLocator，不依赖 Hilt，也不访问 Room。
- 应用只通过两个接口与之交互：一个是守护页入口组件；另一个是由应用提供的“家人号码来源”，只在选择紧急联系人时读取。

**二、开关与权限。**

- 守护默认关闭。只有在这台手机上开启守护时，才申请拨打电话、读取通话状态、发送短信、通知等运行时权限（其中发送短信为可选权限，拒绝不影响开启守护），并引导完成全屏提醒、电池优化、自启动等设置。
- 这些权限由守护模块的 Manifest 声明。这是 ARCHITECTURE 第 31 节“避免直接拨号高权限”的唯一例外，仅用于无人值守的紧急拨号。
- 应用仍然不声明 INTERNET。

**三、紧急联系人。**

- 不再有任何默认号码，原项目中写死的个人号码不迁入。
- 开启守护前必须选择紧急联系人：可以从家人资料中选（列出有在用号码的家人），也可以从通讯录选，或手动输入。
- 所选姓名与号码复制一份到守护的设备加密存储中，保证手机重启未解锁时也能拨号。

**四、解锁前运行（Direct Boot）。**

- 守护组件保持 directBootAware。
- 应用启动时，如果用户尚未解锁，不启动生日提醒同步，也不访问 Room 和 DataStore，避免崩溃；等收到 `ACTION_USER_UNLOCKED` 后再启动。

**五、文案。** 使用“被守护的人”“紧急联系人”等通用说法，不写“爸爸”“儿子”。

**六、迁移提示。** 长辈手机安装家人侠并开启守护后，必须卸载 GuardMyFather，避免重复报警；小米等手机的白名单设置需要对家人侠重新完成。

**七、测试。**

- 状态机的单元测试全部迁入。
- 真机测试使用测试模式（30 秒无活动、15 秒确认），测试号码由用户指定。每次会真实拨号或发短信的测试前，先征得用户同意。

**八、文档。** 新增 `docs/GUARDIAN_MODULE.md`，描述守护的工作原理、状态机、可靠性设计、权限清单与真机回归清单。
